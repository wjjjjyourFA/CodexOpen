# WS_LPNC 框架结构说明

## 1. 核心原则

WS_LPNC 采用“核心算法、通信接口、运行编排”三层分离的结构：

```text
modules/ 或 tools/          核心实现与模块自有配置
          ↑
ros1/src/                    ROS1 进程入口、消息转换、参数装载
          ↑
script/                      多进程组合、日志、启停和可视化
```

这三层的依赖方向是单向的。总控脚本不包含算法，ROS1 适配层不改变
规划、建图或定位公式，核心目录也不放 `launch/package.xml` 等 catkin 编排
文件。

## 3. 有图定位的职责拆分

`Localization_robot` 迁移后使用语义化模块名 `prior_map_localization`：

| 层 | 位置 | 责任 |
| --- | --- | --- |
| 核心 | `modules/localization/prior_map_localization` | 点云预处理、IMU 状态传播、ikd-tree 地图匹配 |
| ROS1 适配 | `ros1/src/localization/prior_map_localization` | topic/frame、RViz 初值、自定义旧消息兼容和进程入口 |
| 参数/资源 | `config/runtime` | 算法 YAML、接口 YAML、先验 PCD、RViz 配置 |
| 编排 | `script/robot_dog_localization.sh` | ROS master、RViz 提前启动、定位进程和日志生命周期 |

先验地图由算法节点启动时发布一次，因此编排层先启动 RViz，再启动定位进程。
RViz 通过公共运行库登记为 optional，监控循环只把定位节点视为 required；关闭
RViz 不会导致定位流程退出。

## 4. 规划流程的职责拆分

`robot_plan_expv2` 和 `robot_plan_path` 是历史实验流程名，不是新框架中的
算法模块名。相关程序
按其输入输出意义归类：

| 模块 | 所属域 | 责任 | 关键输出 |
| --- | --- | --- | --- |
| ROG-Map | 感知 | 将注册点云和位姿转为占据/膨胀地图 | `/rm_node/rog_map/occ` |
| terrain analysis | 感知 | 从地图与位姿提取地形表征 | `/terrain_map` |
| world planner | 规划 | 基于地形和目标生成全局参考路径 | `/global_reference_path` |
| local planner | 规划 | 候选路径评估与局部控制命令生成 | `/path`、`/cmd_vel_corrected` |
| terrain waypoint exploration | 规划 | 前沿探索和下一航点选择 | `/way_point` |
| waypoint publisher | 规划 | 按文件/RViz 目标顺序发布航点、速度和边界 | `/way_point`、`/speed` |

因此 ROG-Map 和 terrain analysis 安置在 `modules/perception`；四个路径或
目标决策程序安置在 `modules/planning`。`robot_plan_stack.sh` 是唯一组合器；
`robot_plan_expv2.sh` 选择地形探索，`robot_plan_path.sh` 选择文件/RViz 航点
发布器。两者共享其余组件和独立开关。

## 5. 模块内部标准

一个可实时运行的模块至少包含：

```text
modules/<domain>/<module>/
├── CMakeLists.txt
├── <core source and headers>
└── config/runtime/
    ├── <Module>.yaml     算法和运行参数
    ├── Interface.yaml    topic、frame 和外部 I/O
    └── <module resources> paths/data/rviz，若需要
```

配置归属规则：

- 改变算法行为的阈值、分辨率和增益归运行参数；
- 连接外部系统的 topic、frame、队列和同步策略归接口参数；
- 路径库归 local planner；`robot_plan_expv2` 的边界航点归 world planner；
  `robot_plan_path` 的 waypoint/boundary 归 waypoint publisher，且 world planner 在该
  流程中共用同一 waypoint 文件；
- 先验定位地图、定位 RViz 和算法参数均归 `prior_map_localization`，不归流程脚本；
- 不再使用一个流程级 `Interface.yaml` 将不同模块绑定。

## 6. ROS1 接口层

`ros1/src` 中的目录镜像 `modules`/`tools` 的业务归属。它只负责：

1. 创建 ROS node 和 NodeHandle；
2. 将模块的 runtime/interface YAML 装载到私有参数空间；
3. 在需要时完成 ROS 消息与核心数据结构的转换；
4. 调用核心程序入口。

`ros1/src/common` 中的 `codexopen_ros1_yaml_param_loader` 是公共适配库，由各模块
链接，避免重复编译同一份 YAML 装载实现。

迁移组件不再由 `ros1/src/.../CMakeLists.txt` 构建，而是由对应核心模块的
`CMakeLists.txt` 将核心和适配入口组合成独立可执行文件。

## 8. 消息链和 TF 边界

默认组合的主要数据链是：

```text
/registered_scan + /state_estimation
       │
       ├──> ROG-Map ──> /rm_node/rog_map/occ
       │                         │
       │                         v
       │                  terrain analysis ──> /terrain_map
       │                                           │
       │                                           ├──> world planner
       │                                           │          │
       └──> terrain waypoint exploration 或 waypoint publisher
                                                   │ /way_point
                                                   │          v
                                                   └──> local planner
                                                             │
                                                   /path + /cmd_vel_corrected
```

该图是默认组合关系，不是编译时强依赖。每个节点只通过话题与其他节点
连接，可由等价的外部模块替换上下游。

有图定位链路独立于上述规划组合：

```text
先验 PCD ──> /world_state/cloud_map ──> RViz
Livox 点云 + IMU + RViz /initialpose
                    │
                    v
        prior_map_localization
                    │
        /state_estimation + /lio/odom
        /registered_scan   + /lio/path
```

TF 约定：

- FAST-LIO 发布 `map -> sensor`；
- prior-map localization 同样发布 `map -> sensor`，两种定位程序不应同时运行；
- 本地规划默认组合发布 `sensor -> vehicle`；
- `/lio/path` 的 header 和每个 pose 均使用 `map`；
- ROG-Map 内部历史 `world/body/drone` frame 暂保持原样；未经标定不在编排层
  自动发布 `map -> world`。

## 9. 迁移不变量

本次拆分只调整了目录、构建目标、参数归属和进程编排。核心 C++ 文件
在移动前后校验值一致，包括 terrain analysis、ROG-Map、world planner、
local planner 和 terrain waypoint exploration。waypoint publisher 先以原文件 SHA-256 一致
的方式导入，后续只拆出进程入口和 topic/frame 接口；航点推进、到达判定、
等待、速度和边界发布逻辑未修改。所有模块均没有借迁移调整参数值。

`Localization_robot` 的 `ImuProcess.cpp`、`MapProcess.cpp`、`PreProcess.cpp` 和
`ikd_Tree.cpp` 按原文件导入并通过逐字节校验。迁移只把路径、topic、frame 和
日志位置移到适配/配置层；旧代码中误读 `mapping/max_iteration` 的键名改为配置
文件实际存在的 `mapprocess/max_iteration`，因此继续使用原配置值 `5`，没有调参。

## 10. 新增模块时的准入规则

1. 先根据数据语义选择 `drivers/localization/perception/planning/control/tools`
   中的准确业务域，不以历史启动脚本名命名模块。
2. 一个核心程序对应一个独立可执行文件，多进程流程放在根 `script/`
   中编排。
3. 核心代码和 ROS1/ROS2/DDS 适配代码保持目录对应，不让一种通信框架
   的启动文件成为核心模块的构建主体。
4. 算法参数和接口参数分文件管理，默认值只做格式迁移，不借框架整理
   调参。
5. 必须同时验证独立目标编译、`ninja install`、`--check` 和至少一种裁剪
   组合。
